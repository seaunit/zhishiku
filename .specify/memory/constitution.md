# Zhishiku 知识库宪法

## Core Principles

### I. 规格驱动开发（NON-NEGOTIABLE）

产品功能和重要变更必须遵循 SDD（Spec-Driven Development，规格驱动开发）流程。实施前必须
形成明确的规格、计划和可执行任务；需求不清晰时，必须先澄清并更新规格，不得直接进入编码。

实现必须与已确认的规格和任务保持一致。若实现过程中发现规格冲突、范围变化或关键假设失效，
必须回到相应阶段更新产物并获得确认，不得以代码实现反向替代需求决策。

### II. 多子智能体协作与职责分离（NON-NEGOTIABLE）

项目必须由产品、开发和测试等多个子智能体共同协作完成，各角色承担明确且不可混淆的职责：

- 产品子智能体负责需求评审、任务分析与拆分，必须输出可执行的需求和验收标准，不得修改代码。
- 开发子智能体负责编码实现，必须依据已确认的规格、任务和验收标准开展工作。
- 测试子智能体负责独立测试与验收，必须依据验收标准验证结果并报告缺陷或风险。

角色交接必须提供明确的任务上下文、产物和验收条件。任何角色不得以完成下游工作为由绕过上游
确认，也不得以其他角色的结论替代自身职责。未解决的规格、实现或验收冲突必须显式上报。

### III. 默认中文的双语交付

项目必须支持中文和英文，默认使用中文。面向用户的文档、界面和交付说明默认以中文完整呈现；
需要英文版本时，英文内容必须与中文版本在事实、范围和验收条件上保持一致。

所有 SDD 过程文档必须使用中文，包括宪法、功能规格、澄清记录、实施计划、研究结论、数据模型、
接口契约说明、任务表、快速验证指南和部署文档。英文只可用于代码标识符、API 字段、协议名称、
文件路径、命令以及无法准确翻译的专业术语；此类术语首次出现时必须同时用中文解释。

中文 SDD 文档是项目复核的权威版本。若后续提供英文同步版本，事实、范围、约束和验收条件发生
冲突时，以中文版本为准。产品界面的中英双语能力不改变本条的文档语言要求。

专有名词、代码标识符、文件名和行业术语必须保持全仓库一致。不得使用机器翻译替代对关键事实、
法律含义、安全说明或验收标准的校对。

### IV. 知识准确性与可追溯性

知识内容必须区分事实、推断和建议。涉及外部事实或关键结论时，必须标注可核验的来源、日期和
适用范围；无法确认的信息必须明确标记为待确认，不得作为确定结论发布。

每份文档必须聚焦一个主题，使用清晰稳定的一级标题和一致的层级结构。仓库内引用必须优先使用
相对链接；移动或重命名文档时必须同步修复引用。内容使用 UTF-8，术语保持一致，并避免复制粘贴
造成的重复知识。

### V. Taste 视觉验证

前端页面或交互原型设计必须使用 Taste 技能（design-taste-frontend）。视觉方案必须服务于知识库
内容与用户任务，并按照该技能要求完成真实浏览器检查、截图审视和必要修复。

交付前必须验证桌面与移动布局、可读性、交互状态、中英文切换和默认中文表现。未经视觉验证的
前端或原型不得声明完成。视觉验证必须以最新已批准原型为基准，不得仅验证前端内部的一致性。

### VI. 外部数据与密钥安全（NON-NEGOTIABLE）

项目不得使用、引入或依赖爬虫技术，包括但不限于站点抓取、网页批量抓取、自动遍历第三方站点
以及绕过访问限制的数据采集。外部数据必须通过经授权的 API、用户主动提供或具有明确许可的
数据源获取。

AI API Key、SMTP 凭证、访问令牌、密码及其他密钥信息必须仅通过环境变量或受管密钥服务注入。
不得将真实密钥写入源代码、配置文件、文档、测试、日志、错误消息、截图、构建产物或版本控制。

仓库只能提交不含真实值的变量名示例。应用启动时必须校验所需环境变量是否存在，但不得打印、
回显或记录其真实值。发现密钥泄露时必须立即撤销或轮换，并审查相关日志和提交历史。

识海是多账号产品，账号可通过邮箱公开注册。注册不得要求图形验证码；发码和注册只依赖邮箱
验证码、密码和确认密码。邮箱验证码必须哈希存储且一次性使用，同一邮箱两次成功发码之间至少
间隔 60 秒，并同时执行邮箱和来源 IP 频率限制、受控临时邮箱域名拒绝、邮箱全局唯一检查。
登录仍必须使用服务端缓存的一次性图形验证码。注册入口不得因实例已有其他账号而关闭。

每个账号必须独立拥有和隔离知识、附件、上传、搜索、会话、AI 授权、点数账户、订单、退款和
账本。任何业务查询、写入、搜索、对象访问、计费预留与结算都必须从已认证会话取得账号身份并
施加账号范围条件，客户端提交的账号标识不得超过会话身份。保留兼容字段 `owner_id`，但其语义
必须是账号 ID，不得重新解释为实例唯一所有者。

多账号不等于团队工作区。本原则不允许跨账号读取、共享知识、成员邀请、团队协作、团队共享
点数或账号间转赠；公开分享也不在范围内。

### VII. GitHub 源码管理与一键部署（NON-NEGOTIABLE）

项目必须使用 GitHub 作为源码、数据库迁移、部署脚本、Nginx 模板和 systemd/容器配置模板的
唯一权威来源。服务器上不得保留无法从 GitHub 重建的手工源码修改；任何必要的运行配置变更必须
同步回仓库。

部署必须提供可重复执行的一键脚本，从官方 GitHub 仓库拉取源码或发布产物后完成：

- 环境与依赖预检。
- 目标版本选择。
- 数据与配置文件备份。
- 依赖安装、构建和数据库迁移。
- 服务启动或重启。
- 健康检查、关键路由验证和失败回滚。

生产部署必须支持指定 Git tag 或 commit；默认分支可标注为最新开发版本，不应无法选择固定版本。
官方仓库地址和默认分支必须在 README 与部署文档中明确。示例入口可以采用：

```bash
curl -fsSL "https://raw.githubusercontent.com/${GITHUB_OWNER}/${GITHUB_REPO}/${GITHUB_REF}/deploy/scripts/provision-ubuntu.sh" | sudo bash
```

入口必须固定使用官方 HTTPS GitHub 地址。脚本必须幂等，重复执行不得重复创建账户、数据库、
密钥或破坏已有数据；不得把真实密钥写入仓库、脚本、日志或命令行历史。部署脚本和 GitHub
Actions 必须执行与改动范围匹配的 lint、类型检查、测试和构建门禁。

一键部署必须兼容现有 `seaunit.site` 应用：不得覆盖其 `/api`、`/app`、`/bank`、`/pay`、
`/apk`、证书和认证配置；知识库必须在 `/kb` 下独立部署，并提供可验证的回滚路径。

### VIII. 现有应用零影响（NON-NEGOTIABLE）

任何知识库开发、构建、部署、迁移、回滚或运维操作都不得影响 `seaunit.site` 原有应用的
运行。原有应用包括 Spring Boot 服务、支付侧车、MySQL、Redis、Nginx、TLS 证书、认证
Cookie、静态站点和 Cloudflare 接入。

部署前必须记录并验证原有应用的基线健康状态，至少覆盖 `/`、`/app`、`/api`、`/bank`、
`/pay`、`/apk` 和证书可用性。部署后必须以相同检查证明原有功能未发生回归。

知识库必须使用独立的系统用户、进程、端口、环境文件、数据库、对象存储、Cookie 名称和日志。
不得复用原有应用的用户、数据库、Redis、运行目录、环境变量或认证 Cookie。端口必须绑定回环
地址，外部只通过 Nginx 的 `/kb` 路径访问。

Nginx 变更必须保持增量：既有的 `/api`、`/app`、`/bank`、`/pay`、`/apk`、证书和根应用路由
不得被替换、覆盖或删除。每次变更前必须备份配置，执行 `nginx -t`，失败时不得 reload，并必须
能够恢复到变更前配置。

一键部署脚本必须在预检阶段验证原有应用健康、磁盘与内存余量、端口冲突和路由冲突。任何检查
失败必须 fail closed，不得停止、重启、迁移或修改原有服务。若部署需要改动原有应用，必须停止
当前部署并作为独立的 SDD 变更获得明确批准。

### IX. 任务完成可追溯（NON-NEGOTIABLE）

任务完成状态必须与实现、验证和记录保持同步。每完成一个 `tasks.md` 中的任务，必须立即把对应
复选框从 `- [ ]` 更新为 `- [x]`，不得在任务未完成或未验证时提前标记。

每个已完成任务必须在该任务的 `## Completion Log` 中增加独立记录，至少包含：

- 任务 ID、完成日期和当前状态。
- 简洁的完成摘要。
- 具体任务详情，包括实现内容、关键决策和变更文件。
- 实际执行的验证命令、检查结果和证据路径。
- 对应的 Git commit hash；尚未提交时必须明确标记未提交，不得声称已归档。

完成记录必须可审计，不得用“已完成”“测试通过”等无证据描述代替摘要、详情和验证结果。
缺少验证证据、存在未解决阻塞或依赖尚未完成时，任务不得标记完成。

若已完成任务被重新打开，必须把复选框恢复为 `- [ ]`，并在完成记录中追加重新打开日期、原因和
后续要求；不得删除既有历史记录。任务勾选、完成记录和对应代码/文档必须尽量在同一逻辑变更中
提交，确保 GitHub 历史可以重建任务状态。

### X. 支付与点数完整性（NON-NEGOTIABLE）

付费 AI 能力必须使用明确的一次性点数包和版本化点率。MVP 采用 Waffo 个人支付与人民币
结算，不得在未新增规格和批准的情况下销售订阅、自动续费或未经用户再次确认的扣款。

支付订单只能依据签名有效且通过金额、币种、商品、订单和环境核验的 Waffo 通知，或经过
授权验证的 Waffo 主动查询结果进入已支付状态。浏览器成功跳转、用户声明或前端参数绝不能
直接增加点数。支付通知与主动查询必须共享同一订单终态和幂等边界，状态冲突进入可追踪异常。

点数账户必须使用只追加明细和可追溯来源批次。体验点与购买点分别记录；消费按体验点优先、
购买点最早批次优先。AI 任务必须先取得费用预估和确认、原子预留上限内点数，再按成功步骤
结算；失败、取消、超时或没有有效结果必须释放。任何并发、重试、回调重放或进程恢复都不得
造成负余额、超预估扣费或重复扣费。

自动整理扣点授权必须与外部 AI 处理隐私授权分离，默认关闭，并受单次和每日用户上限约束。
余额不足或超过上限时，内容仍必须保存并转入待整理状态，不得阻止知识入库。

退款、部分退款、点数回收和人工调整必须可审计且幂等。退款只能回收原订单批次中尚未使用的
点数；无法全额回收时不得使余额为负，必须进入有负责人、有期限、有最终结论的人工复核。
测试和生产必须使用独立的商户、商品、密钥、收银台、返回地址、通知、订单与点数账本，
测试支付不得增加生产点数。

知识库支付、订单、账户、数据库、Cookie、运行目录、端口和通知路由必须与现有拾题应用完全
隔离。不得复用或改写其 `/pay`、余额、支付侧车、密钥或认证配置。Waffo 私钥和其他支付凭据
只能通过环境变量或受管密钥服务提供，不得出现在源码、文档、日志、截图、错误消息或构建产物。

### XI. 原型与前端一致性（NON-NEGOTIABLE）

最新且已批准的原型是前端视觉和交互的唯一事实源。前端主题、导航与菜单结构、页面布局、字体、
颜色、间距、组件形态、响应式行为、交互状态和中英文呈现必须与原型一致；实现不得自行形成另一套
视觉系统。

原型发生变更时，必须同步评估受影响的规格、任务和前端实现。已批准的原型变更必须触发对应的
前端修改，并在同一逻辑变更中完成；不得只修改原型而长期保留旧前端，也不得只修改前端而不更新
原型和 SDD 产物。

若实现受无障碍、性能、数据约束或平台能力限制，确实无法完整还原原型，必须在编码前说明差异、
理由和替代方案，并先获得产品确认；批准后必须同步更新原型或形成可追溯的差异记录。未经确认的
视觉偏差不得以“技术实现更合理”为由保留。

前端验收必须提供最新原型与实现页面的对照证据，至少覆盖桌面和移动端的主题、侧栏或顶部导航、
菜单项、关键页面、交互状态和中英文切换。缺少对照证据或存在未批准的视觉偏差时，任务不得
标记完成。

## Additional Constraints

本仓库用于构建和维护知识库，不是单纯的代码仓库。内容以 Markdown 为主，强调准确性、可检索性、
可维护性和可追溯性。仓库已经初始化 Vue 3、Spring Boot、PostgreSQL、部署脚本和自动化测试；
所有文档必须以实际配置文件、锁文件和已部署版本为准，不得虚构不存在的命令、框架或工程约定。

### 知识采集边界（NON-NEGOTIABLE）

手动录入是唯一允许不经过 AI、直接保存用户原文和手动插入正文图片的采集方式。

AI 文字、网页链接、文档文件、文档入口图片、剪贴板截图和互联网搜索结果都必须经过
“提取或 OCR、密钥脱敏、外部 AI 结构性整理、原子入库”的完整流程。服务端必须拒绝通过普通
知识创建接口提交 `document`、`screenshot`、`internet_result` 或 `text` 来源绕过 AI。

原始 URL、文件名、原文件、原截图、搜索摘要和提取全文不得直接成为知识正文。非手动处理缺少
外部 AI 授权、生产计费门禁未满足、无有效文本、AI 失败或任一知识写入失败时，必须零知识写入，
不得保存原文、图片-only 或部分结果。互联网候选只能通过已授权单页 Fetch 获取内容，并在 AI
整理成功后才进入知识库。

所有变更必须保持范围聚焦，不得进行与任务无关的重构、格式化或批量重写。不得覆盖、删除或重排
用户已有内容，除非任务明确要求。新增依赖前必须说明必要性，并优先使用标准库和已有依赖。

仓库不得提交密钥、令牌、个人隐私数据、构建产物、缓存或本地环境文件。知识内容必须避免未经
授权或无法追溯的敏感信息。

付费、订单、点数、退款、点率、环境和财务对账行为必须以中文 SDD 文档明确记录。任何商业参数
变化必须形成版本化规格或计划修订，并同步更新用户可见价格、配额和退款说明。

## Development Workflow and Quality Gates

开发工作流必须依次覆盖需求评审与规格、任务拆分、实现、测试和验收。产品子智能体在编码前完成
需求评审、任务分析与拆分，并定义可验证的验收标准；开发子智能体负责实现；测试子智能体负责
独立测试和验收。

交付前必须根据改动范围执行可得检查：

- 文档改动检查标题层级、相对链接、代码块、拼写和事实一致性。
- 配置改动解析配置并确认引用路径、环境变量和默认值有效。
- 代码改动依次执行仓库现有的 lint、类型检查、测试和构建命令。
- 前端或原型改动执行 Taste 技能规定的浏览器与视觉检查。
- 前端改动必须与最新已批准原型逐项对照主题、导航、布局、组件、响应式布局和交互状态；原型
  变更与对应前端实现必须处于同一交付边界内，并将对照截图作为验收证据。
- 支付或计费改动执行订单状态机、签名通知、主动对账、并发扣费、退款批次、环境隔离、
  密钥泄漏和原有应用零影响检查。
- 若仓库已初始化 Git，至少运行 `git diff --check` 检查空白错误。

缺少测试、验证命令或视觉检查条件时，交付说明必须明确列出未覆盖风险，不得声称“已验证通过”。
评审必须优先关注错误信息、失效链接、数据泄露、不可复现步骤、无障碍问题、行为回归和事实错误。

## Governance

本宪法是项目治理的最高约束。`AGENTS.md` 是日常协作与运行时指导，不得与本宪法冲突；若两者
冲突，以本宪法为准，并必须在同一变更集中同步修正 `AGENTS.md`。

宪法修订必须经过产品评审和明确批准，并说明修订理由、影响范围和迁移要求。每次修订必须更新
版本号和最后修订日期，并在评审中验证相关原则是否得到满足。

版本号采用语义化版本：
