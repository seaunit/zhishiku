# 研究结论：Dify AI 编排

**日期**：2026-10-27

## 本地 Dify 接入

**决策**：通过 `POST /v1/workflows/run` 调用识海独立工作流；阻塞模式用于知识整理和非流式聊天，流式模式用于用户可见回答。

**理由**：工作流 API 提供确定性输入、结束节点输出和 SSE 事件，后端可以统一校验和转换，不需要把 Dify 的会话系统暴露给前端。

**替代方案**：

- 直接使用 Dify Chat API：会引入 Dify 会话状态，与识海自己的会话表和引用校验重复。
- 让 Dify 连接识海数据库：破坏账号隔离、幂等和事务边界。
- 在前端直接调用 Dify：会泄露 API Key，无法保证计费和脱敏。

## 本地端口异常

**决策**：本次本地联调使用 `127.0.0.1:8502` 的独立 Dify Nginx 桥接；正式配置仍由环境变量指定，不把该临时端口写死到业务代码。

**理由**：Dify API、Worker、PostgreSQL 和内部 Nginx 均健康，但 Docker Desktop 的宿主 `8501` 发布端口建立连接后无响应。新增桥接复用现有 Dify Nginx 镜像和配置，只发布一个新的回环端口，不修改原容器。

浏览器访问 Dify 控制台时必须使用 `http://localhost:8502/`。Dify Web 将 API 固定为
`http://localhost:8501`，若从 `127.0.0.1:8502` 打开控制台，登录请求会被浏览器视为跨站，
登录接口返回 200 后 `SameSite=Lax` Cookie 仍不会随工作区请求发送，最终表现为登录失败。
后端 Java 进程不依赖浏览器 Cookie，可以继续使用 `http://127.0.0.1:8502/v1`。

**替代方案**：

- 重新安装或重启 Docker Desktop：影响面过大。
- 修改 Dify compose 的既有端口：可能影响用户当前使用方式。
- 在业务代码中使用 Docker 容器 IP：不可移植。

## 提供商选择

**决策**：新增 `SHIHAI_AI_ORCHESTRATION_PROVIDER`，支持 `deepseek` 和 `dify`。本地测试配置设为 `dify`；生产默认仍为 `deepseek`，直到单独完成生产 Dify 发布审批。

**理由**：显式选择可以单独回滚 AI 提供商，不影响数据库、前端或支付。

**替代方案**：

- 自动探测 Dify 后切换：会让部署结果不可预测。
- 删除 DeepSeek 直连：失去故障回退和现有测试基线。

## 工作流拆分

**决策**：创建 `shihai-knowledge-organizer` 和 `shihai-xiaoshi-chat` 两个工作流。聊天工作流通过 `operation` 输入区分知识回答、通用回答、检索计划、联网回答和流式回答。

**理由**：知识整理输出和聊天输出有不同契约；聊天内部操作共享大部分安全指令，MVP 使用单一工作流可以减少密钥和运维数量。

**替代方案**：

- 每种操作一个应用：配置和密钥数量过多。
- 一个工作流同时处理整理与聊天：输入、校验和权限边界不清。

## 结构化输出

**决策**：Dify 输出仍由后端解析、长度限制、URL 过滤、引用校验和富文本映射。知识整理要求 JSON；聊天按操作返回 JSON 或纯文本。

**理由**：Dify 的模型输出不是业务事实，不得直接信任。

**替代方案**：

- 依赖 Dify 结构化输出节点：仍不能替代后端业务校验。
- 直接把模型文本写入数据库：会破坏现有安全和一致性规则。

## 超时、重试与流式

**决策**：连接和读取复用有限超时；只对连接失败、HTTP 5xx 和明确的瞬时错误做最多一次重试。流式请求一旦向用户发送文本，不自动重试，避免重复输出。

**理由**：AI 请求可能耗时且非幂等；自动重试可能重复扣费或生成不同内容。

**替代方案**：

- 无限重试：会放大故障和费用。
- 流式中断后静默重试：会拼接两段不一致回答。

## 日志与审计

**决策**：应用日志只记录提供商、操作类型、耗时、状态、脱敏错误码和 Dify 运行 ID；不记录密钥、正文、问题、证据或完整上游响应。

**理由**：满足排障需要，同时避免知识内容和身份信息进入日志。

**替代方案**：

- 记录完整请求：泄露风险不可接受。
- 完全不记录：难以定位超时和契约不一致。
