# 阶段 0 研究：识海 AI 点数计费与 Waffo 支付

**功能**：`002-ai-credit-billing`

**检查日期**：2026-10-21

**来源说明**：本文依据现有服务器的只读检查、Waffo Pancake SDK 接入代码和功能 001
技术计划形成。服务器上的私钥、商户密钥、商品 ID、订单和用户数据均未写入本文。

## 研究范围

需要解决以下问题：

1. 识海采用哪些点数包和结算方式。
2. Waffo 应接入主应用还是独立桥接进程。
3. 如何保证到账、扣费、释放和退款只发生一次。
4. 如何使用可追溯批次落实体验点与购买点消费顺序。
5. 如何在不阻塞知识入库的前提下处理余额不足和自动扣点。
6. 如何隔离测试/生产环境并处理通知缺失、乱序和冲突。
7. 如何验证单位经济性、双语体验和原有拾题零影响。

## 决策 1：一次性人民币点数包，使用独立识海 SKU

**决策**：MVP 只销售三个一次性点数包：

| 识海 SKU | 售价 | 点数 |
|----------|------|------|
| `kb_pack_9` | CNY 9.00 | 400 |
| `kb_pack_29` | CNY 29.00 | 1,400 |
| `kb_pack_99` | CNY 99.00 | 5,000 |

不销售订阅，不使用拾题的 `pack_9`、`pack_29`、`pack_99` 商品代码或商品映射。

**理由**：现有参考应用已验证三档一次性点数包的购买体验和价格梯度，但识海必须拥有独立
商品代码和 Waffo 商品，避免订单、退款、测试环境和商品配置发生语义碰撞。

**考虑过的替代方案**：

- 直接复用拾题商品：无法独立控制测试/生产状态，退款和报表会混淆，拒绝。
- 自定义金额：支付和风险控制更复杂，不利于 MVP，拒绝。
- 订阅：用户要求点数制，且当前不需要周期性扣款，拒绝。

## 决策 2：独立 Waffo 桥接，不复用拾题支付侧车

**决策**：新增 `bridges/waffo` Node.js 桥接，仅负责 Waffo SDK、原始通知验签、受控订单
查询和安全化事件转发。Spring Boot 计费核心拥有订单与账本；桥接不拥有 PostgreSQL、
不读取知识正文，也不处理点数结算。

桥接收银台以本地 UUID `orderId` 作为稳定幂等键；创建成功但响应丢失时，先按
`orderMerchantExternalId=orderId` 查询并恢复已有会话，再决定是否新建。

**理由**：Waffo 私钥、签名和原始交易载荷与知识内容分离后，Spring Boot API/Worker 不需要
直接暴露 Pancake SDK；桥接故障不会破坏知识库免费功能。保留 Node 是因为现有 SDK 和
参考实现属于 TypeScript，避免无依据重写验签语义；独立进程也便于固定版本部署和回滚。

**考虑过的替代方案**：

- 直接复用 `shuati-payments.service`：会耦合两套应用的密钥、商品、路由和发布节奏，
  违反零影响原则，拒绝。
- 将 Waffo SDK 直接放入长生命周期 Web 进程：少一个进程，但扩大支付风险和发布耦合，
  不作为首选。
- 每次支付启动临时 CLI：无法稳定处理通知和主动查询，拒绝。

## 决策 3：PostgreSQL 是订单和点数的唯一权威

**决策**：订单、支付事件、点数账户、批次、预留、明细、退款和对账均写入 PostgreSQL 18。
Meilisearch 不保存任何计费事实，前端缓存不得作为余额权威。

**理由**：到账与扣费需要跨多行原子事务、唯一约束、行锁和恢复能力；PostgreSQL 已作为
功能 001 的权威数据源，不额外引入账务数据库或 Redis。

**考虑过的替代方案**：

- 仅用 Waffo 查询结果作为余额：无法表达本地 AI 消费与批次，拒绝。
- Redis 计数器：持久性和审计不足，拒绝。
- 独立账务数据库：增加运维和一致性成本，MVP 无必要，拒绝。

## 决策 4：不可变明细加可核对投影

**决策**：所有点数变化写入只追加账本。账本明确记录 `available_delta`、
`reserved_delta` 和 `consumed_delta`，账户可用余额、批次剩余量和任务冻结点数是可重算
投影，不能由客户端直接覆盖。金额使用人民币最小单位整数，点数使用整数。

**理由**：发生争议时可以从批次和账本重建余额；整数避免浮点误差。唯一业务操作键防止同一
任务或事件重复记账。

**约束**：

- 账本唯一键至少包含操作类型、关联类型和关联 ID。
- 同一幂等键不同请求体必须返回冲突。
- 任何事务结束后可用余额不得小于零。
- 账本不随知识条目删除而级联删除。

## 决策 5：订单快照与环境绑定

**决策**：订单保存识海 SKU、桥接返回的 Waffo 商品 ID 快照、价格版本、金额、币种、点数、环境、收银台
会话和状态时间线。价格或点率后续变化不追溯历史订单。

同一所有者在同一环境、同一 SKU 快照的 `PENDING` 订单使用部分唯一约束，重复点击或并发
请求只能得到一笔可付款订单；迟到支付确认时原子关闭同 SKU 的新待支付订单。
`WAFFO_PRODUCT_MAP` 是供应商商品 ID 的唯一权威。

**理由**：报价、支付、退款和财务汇总必须使用同一购买事实。环境绑定可防止测试会话或商品
进入生产账本。

**考虑过的替代方案**：订单只保存 SKU 并在查询时读取当前价格，无法证明用户当时支付的
金额，拒绝。

## 决策 6：签名通知与主动查询共享归一化结果

**决策**：Waffo 通知使用原始请求体验签，记录事件唯一键、环境、事件类型和处理结果。
Worker 主动查询未决订单，并将查询结果转换为同一套内部支付事实。两者进入同一订单状态机
和幂等事务。

**理由**：仅依赖通知会在网络、部署或供应商重试失败时永久卡单；仅依赖轮询会增加延迟。
双通道能兼顾到账时效和恢复能力。

**约束**：

- 浏览器返回页只显示“确认中”，不得加点。
- 首个可靠已支付事实使订单进入 `PAID`；后续相反状态不自动撤回。
- 通知、查询和退款乱序时保留事件顺序并进入人工复核。
- 重复事件返回成功或幂等结果，不改变余额。

## 决策 7：原子报价、预留和按成功步骤结算

**决策**：AI 任务开始前生成版本化报价，列出各步骤、计费单位、单价和总上限。用户确认
或匹配有效自动扣点授权后，一次性预留总额；余额不足则整个任务不执行。成功步骤结算，
失败步骤释放，实际扣费不超过上限。

**理由**：用户必须在执行前知道最坏费用；分步骤结算又能避免失败步骤收费。任务级预留让并发
扣费和无余额执行变得可验证。

**考虑过的替代方案**：

- 执行后按实际消耗直接扣费：存在余额不足后欠费或中途停止的体验，拒绝。
- 按比例预扣固定 50%：无法覆盖组合任务上限且解释困难，拒绝。
- 每个子步骤单独确认：破坏批量导入体验，不作为默认。

## 决策 8：点数批次消费与退款回收

**决策**：体验点是独立批次；每个已完成订单生成独立购买批次。消费顺序固定为体验点优先、
购买点按购买时间最早优先。退款冻结对应批次并只回收其未使用点数。

**理由**：只有来源批次才能准确回答“退款应回收哪一笔点数”。固定顺序让用户和测试都能预测
余额变化，避免随意选择批次。

**退款规则**：

- 全额退款可自动回收原订单批次剩余点数；运行中任务的批次分配进入 `refund_hold`，
  任务结束后新释放点数继续进入同一退款案例。
- 部分退款、重复退款、已消费点退款和异常金额进入人工复核。
- 已开始任务可完成并结算；未开始任务取消并释放。
- 无法回收时不得产生负余额；未回收部分记录财务异常。

## 决策 9：自动扣点使用独立授权和硬上限

**决策**：外部 AI 处理授权不代表允许扣点。自动整理扣点默认关闭，用户单独设置单次和每日
上限；首次默认建议单次 15 点、每日 100 点。保存前显示本次预计扣点和余额。

**理由**：功能 001 需要自动化，但静默消费会破坏信任。独立授权同时保留用户选择自动化的
能力。

**降级行为**：授权关闭、超过限额、余额不足或支付不可用时，手动内容仍成功保存并进入
待整理状态；不执行付费 AI，不产生扣费。

## 决策 10：测试与生产硬隔离

**决策**：测试和生产分别配置物理 PostgreSQL 数据库、商户/店铺、商品、私钥、返回 URL、
通知 URL、订单、账本、Cookie 和日志标识。启动时以 `BILLING_DB_ENV` 校验数据库身份；
生产发现测试商户、测试商品、测试数据库或测试通知地址必须失败关闭。

**理由**：相同回调结构容易误把测试商品事件发送到生产。不可变环境标识和独立商品映射比
“按当前配置猜测环境”更可靠。

**考虑过的替代方案**：同一套商品按金额大小判断环境，无法防止重放和配置误用，拒绝。

## 决策 11：与拾题应用不共享支付资源

**决策**：识海使用独立 `/kb` 路由、独立数据库/表、独立 Cookie、独立订单和独立
环境文件。支付通知位于 `/kb/pay/webhooks/waffo`，桥接端口为 `127.0.0.1:8091`。

**不得复用**：

- `/pay/webhooks/**`、`shuati-payments.service`、端口 8090。
- `/opt/shuati/payments/` 和 `/etc/shuati/payments.env`。
- 拾题 MySQL、Redis、用户余额、订单、商品映射、认证 Cookie 或密钥。
- 拾题部署脚本对支付配置的写入路径。

识海内部事件 API `/kb/api/internal/` 在 Nginx 直接返回 404，桥接到 Web 的内部密钥只作为
第二道防线。

**理由**：支付通知和账务是高风险边界，隔离失败会直接影响现有应用。

## 决策 12：价格、税费与退款信息在付款前披露

**决策**：价格页显示含税 CNY 最终应付金额、点数、一次性属性、有效期、退款规则、点数
不可提现/转让和客服退款入口。任何额外费用必须在进入收银台前显示。

**理由**：避免收银台金额跳变和退款争议。Waffo 商品价格在创建时使用含税数字商品配置，
但识海仍需向用户展示相同事实。

**考虑过的替代方案**：收银台才显示税费，无法满足付款前知情，拒绝。

## 决策 13：测试分层与发布门禁

**决策**：

- JUnit 5、AssertJ 与属性测试：状态机、批次优先级、报价取整、退款边界。
- Testcontainers：Spring 事务、并发预留、通知幂等、退款与预留竞态。
- RestAssured、JSON Schema 和 WireMock：Spring 计费 OpenAPI、Node 桥接契约和错误码。
- Vitest：Vue 价格、余额、确认、异常和退款状态。
- Playwright：测试支付到账、余额不足、自动扣点、退款和双语。
- k6：100 组并发扣费、订单峰值和对账积压。
- Semgrep、Gitleaks、Trivy：密钥、日志、依赖和容器/制品安全。

**发布门禁**：P0 计费测试未通过不得开启真实收费；P1 退款、对账和零影响未通过不得公开
销售；所有成功标准要有可复现证据。

## 决策 14：单位经济性在公开销售前冻结

**决策**：使用 90 天基准使用组合，将 DeepSeek、截图、OCR、搜索、存储、重试和基础设施
可变成本映射到三个套餐。每个套餐可变成本不得超过收入 50%，整体目标毛利不低于 60%。

**理由**：套餐不能仅因参考应用采用同一价格就视为已批准。实际点率、使用频率和失败重试
成本必须由产品与测试在发布前共同验证。

**未通过时**：调整 AI 点率、套餐点数或价格，创建新的点率版本；不得静默减少已售点数或
追溯扣费。

## 已解决的未知项

- 支付商品：三个独立识海 SKU，一次性 CNY。
- 计费核心：Java 21 + Spring Boot 3.x。
- 支付集成：独立 Node Waffo 桥接，不复用拾题 sidecar；Spring Boot 是账本权威。
- 账本：PostgreSQL 只追加明细加可重算投影。
- 到账依据：签名通知与主动查询，共享幂等状态机。
- 扣费：原子报价、任务级预留、按成功步骤结算。
- 余额不足：内容保存为待整理，不阻断入库。
- 自动扣费：独立授权、默认关闭、单次/每日上限。
- 退款：批次冻结、全额自动保守回收、其余人工复核。
- 环境：测试/生产独立商户、商品、地址、订单和账本。
- 共存：独立 `/kb` 路由、端口 8091、数据库和环境文件，不影响拾题。
- 验证：契约、并发、退款、对账、双语、Taste 和零影响回归。

## 阶段 0 已知风险

1. 现有主机内存余量不足，增加桥接和完整知识库仍需容量审批。
2. 实际 Waffo 查询和退款字段需在测试环境固定脱敏样例后才能冻结最终契约。
3. 三档价格和 AI 点率仍属于草案，必须经过产品批准与单位经济性测算。
4. 人工退款复核的具体客服渠道必须在实现前配置并写入价格与订单页面。
